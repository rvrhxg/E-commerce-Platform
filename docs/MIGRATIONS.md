# Версионированная схема

Alembic 0001 создаёт исходные таблицы и ограничения; 0002 добавляет составной индекс `(user_id, id)` для страниц заказов. `database()` выполняет upgrade head для локального однопроцессного MVP. В окружении с несколькими экземплярами миграции нужно выполнять отдельным deployment job перед запуском приложения; конкурентный запуск миграций не поддерживается.

```sh
python -m alembic upgrade head
python -m alembic current
python -m alembic history
python -m alembic check
```

DATABASE_URL задаётся через окружение; без него используется локальная SQLite. Docker содержит конфигурацию и версии миграций. Изменения моделей сами по себе схему не меняют: создайте revision, проверьте её и добавьте тест обновления.

## База от предыдущей версии MVP

Остановите приложение и сделайте резервную копию. Если схема точно соответствует исходной версии (таблицы users, sessions, products, orders, order_items и их ограничения), выполните `python -m alembic stamp 0001`, затем `python -m alembic upgrade head`. Stamp только записывает номер версии и не проверяет схему — нельзя применять его к произвольной базе. После обновления выполните `python -m alembic check` и проверьте данные. Автоматического распознавания и маркировки старых баз нет.

Тест проходит 0001 → 0002 → 0001 → 0002, сохраняет пользователя и заказ и проверяет отсутствие рассогласования моделей и схемы. Downgrade до base удаляет данные; это инструмент для одноразовой тестовой базы, не процедура восстановления. Для реальных данных восстановление планируется из проверенной резервной копии.

Программное подключение миграций следует [официальному cookbook Alembic](https://alembic.sqlalchemy.org/en/latest/cookbook.html#sharing-a-connection-across-one-or-more-programmatic-migration-commands).
